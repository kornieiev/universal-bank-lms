### 1 Вибір стеку

#### 1.1 Backend: NestJS (Node.js + TypeScript)
Пояснення:
- чітка модульна структура, яка в подальшому легше масштабуватиметься
- вбудована підтримка DTO + validation pipe, що спрощує обробку невалідних даних. Для помилок валідації повертається `422 Unprocessable Entity` з читабельним описом полів
- зручна інтеграція JWT, auth, guards, interceptors
- краща підтримуваність порівняно з чистим Express
- trade-off: більше boilerplate ніж у Express

#### 1.2 Frontend: Next.js (React + TypeScript, App Router)
Пояснення:
- швидка побудова продакшн-структури, роутинг і split by routes
- React екосистема (TanStack Query, react-hook-form, zod) ідеально під login/courses/leaderboard
- навіть якщо зараз майже усе CSR, NextJS дозволяє інтегрувати SSR/edge у майбутньому
> JWT-token у тестовому завданні зберігається у `localStorage`, бо час на виконання обмежений і налаштування `HttpOnly` cookie з CORS/credentials потребує більше часу. У реальному проєкті я би зберігав JWT у `HttpOnly` cookie, щоб зменшити ризики XSS.

#### 1.3 БД: PostgreSQL
Пояснення:
- надійна реляційна модель для `users/courses/enrollments`
- дозволяє легко робити ranking, aggregates, indexes для leaderboard
- хороша сумісність з Docker і ORM

#### 1.4 ORM: TypeORM
Пояснення:
- TypeORM обрано через більший практичний досвід, що зменшує ризики при обмеженому часі
- добре інтегрується з NestJS через декоратори, модулі та стандартний repository pattern
- дає зручний QueryBuilder, корисний для leaderboard, агрегатів і кастомних вибірок
- підходить для реляційної моделі `users/courses/enrollments` і міграцій у PostgreSQL
- дозволяє писати як високорівневий CRUD, так і більш точні SQL-запити
- trade-off: порівняно з Prisma має слабший DX, менш строгий type-safety на рівні запитів і вимагає дисципліни в міграціях та relation-моделях

### 2. Структура проєкту

#### 2.1 Формат: Monorepo
Пояснення:
- в одному репо простіше запустити весь проєкт однією командою
- єдині стандарти lint/format/TypeScript
- можна тримати в shared-папці спільні типи контрактів API

#### 2.2 Layers на backend
Пояснення:
- `controllers` — тільки HTTP-шар, валідація DTO, мапінг відповіді
- `services` — бізнес-логіка (enroll + coins, leaderboard rules)
- `repositories` — доступ до БД через TypeORM `Repository<Entity>` / QueryBuilder
- окремо auth-модуль для реалізації JWT-стратегії і guards

### 3. Інфраструктура

#### 3.1 Docker Compose: 3 сервіси
- `postgres`
- `backend`
- `frontend`

Це мінімальний набір для швидкого старту і рев'ювінгу для цієї таски без зайвих залежностей. При потребі подальшого розвитку можна пізніше додати nginx / redis

#### 3.2 Запуск проєкту відбувається по команді:
Команда:
```bash
    docker compose up --build
```
- Піднімається БД
- Бекенд чекає запуск БД, застосовує міграції і seed
- Фронтенд стартує і звертається до бекенду по внутрішній мережі compose, тобто усі сервіси спілкуються між собою по іменах контейнерів.



### 4 Масштабування

#### 4.1 Leaderboard на великих обсягах (10000+):
- Перейти від «рахувати на льоту» до precomputed ranking.
    - Варіант 1: Redis Sorted Set для near real-time ранжування.
    - Варіант 2: materialized view / агрегована таблиця в Postgres, оновлення background job-ами (крон-джоба кожну хвилину).
- Додати індекси: users(coins desc), enrollments(user_id, progress, completed_at).
- Повернення current_user окремим легким запитом, навіть якщо не в top-10.

#### 4.2 Кешування:
- GET /api/courses: TTL кеш (дані рідко змінюються).
- GET /api/leaderboard: короткий TTL (наприклад 15-30 сек) + інвалідація після подій, що впливають на coins.
- Профіль і мої курси: або без кешу, або дуже короткий per-user кеш.
- На frontend: TanStack Query cache для моментального UX і background refetch.

#### 4.3 Пагінація на бекенді для розділення великів наборів даних, наприклад на запити:
- GET /api/courses
- GET /api/users/me/courses


### Додаткові покращення, які можна було б зробити за наявності більше часу

+ ДОДАТИ пагінацію на бекенді для списку курсів / leaderboard / користувацьких enrollments
+ Перевірити обробку помилок і ексепшнів при різних умовах виконання запитів
+ Написати валідацію змінних оточення, щоб додаток коректно працював у різних середовищах
+ Додати юніт- та інтеграційні тести для backend і frontend

+ У відгуку `GET /api/leaderboard` зараз повертається `userId` для того, щоб коректно відображати поточного користувача в таблиці. Це трохи виходить за межі початкового ТЗ, але було додано для зручності перевірки та підсвічування поточного користувача на клієнті.

### Auth
> Хоча в ТЗ не було необхідності реалізовувати `refreshToken`, я все одно додав refresh-токен у бекенд/фронтенд, щоб зробити аутентифікацію більш реалістичною і стійкою до закінчення сесії.
